# GameBench 0.6 Benchmark 设计审查

## 结论

**作为“编码 Agent 在公开契约下的一次性交付测试”，设计基本合理；作为通用游戏开发能力、游戏体验或稳定模型实力排名，证据不足。** 应保留轻量评测架构，优先加强测试自身的质量控制与分数解释，而不是增加 Docker、服务、人工打分或另一套排名。

本次审查以冻结的 `benchmark/releases/0.6.0.json` 为基线，未修改既有 task、prompt、测试断言、权重、release lock 或历史结果。随后按维护者要求将非评分优化纳入 0.6.1 补丁：新增锁文件仅 `benchmark_version` 不同，不重新计算历史分数，详见[0.6.1 发布说明](releases/0.6.1.md)。

## 合理之处

| 设计 | 判断与边界 |
| --- | --- |
| 2048、扫雷、停车、六人德扑 | 分别探测离散规则、隐藏状态、连续模拟、复杂状态机，覆盖互补；只有四题，不能代表整个游戏开发领域。 |
| 一次开发、源码冻结、全新目录评测 | 防止在看到评测结果后修补交付；重复评测同一源码只测评测器稳定性，不是新模型样本。 |
| 四题各 100 分、等权平均 | 透明、可解释，且不因缺题而提高均分；等权不意味着题目难度相等。 |
| 构建/服务/Bridge/初始 Schema 硬门槛 | 保证交付可被评测；一个初始 Schema 错误也会丢掉整题，需要同时报告失败原因，不能把所有零分解释成规则能力为零。 |
| 预检、基础设施失败不记模型零分 | 故障归属原则正确；需通过故障注入验证分类路径，而不只测试正常路径。 |
| 预注册 Campaign、固定系列 ID、整批发布 | 限制同一实验内挑选最好结果；不能自动消除实验外的选择性发布或跨日期、跨提供商混杂。 |
| 公共案例和原生输入 | 容易审计，但测试可见，且大多数结果仍由交付自身的 snapshot 报告；不能宣称隐藏泛化或完整 UI 真实性。 |

## 当前测试结构

| 任务 | 评分 case 数（含 build） | 浏览器 case 数 | 含原生输入的 case 数 | 最大单 case 分值 |
| --- | ---: | ---: | ---: | ---: |
| 2048 | 10 | 9 | 2 | 20 |
| 扫雷 | 10 | 9 | 1 | 20 |
| 停车 | 10 | 9 | 1 | 15 |
| 德扑 | 11 | 10 | 1 | 15 |

总计 41 个评分 case，其中 37 个浏览器 case、5 个包含原生输入，当前没有截图断言。这里统计的是测试覆盖结构，不是 41 个独立模型样本。单个 20 分案例失败会让 Build 总分下降 5 分：所谓“原子积分”仍然有较粗的全有或全无粒度，尤其需要正反例校准。

`results/lite/index.json` 当前七个系列共 28 个任务结果，其中 7 个触发 hard gate。2048 分数均在 90–100；扫雷只有 100 或硬门槛零分，没有中间分。这批样本提示简单题可能接近天花板、部分区分来自 Schema 交付合规性；但样本小且来自不同系统/Campaign，不能据此事后改权或推断总体难度。

## 发现的问题与优化边界

### 1. 测试定义存在“校验通过但评分映射不可靠”的入口 — 本次修复

原 `TestSuiteSchema` 未要求 case ID 唯一，评测器又按 ID 把结果写入 `Map`，后一个 case 可以覆盖前一个。空步骤或只有动作的 browser case 也能自然返回通过。任务校验此前只检查引用是否存在，未检查：

- 多个评分项引用同一 case，造成重复计分和虚假的原子粒度；
- 执行了没有评分项的 case，其失败不能在最终测试向量中表达；
- build 类别引用 browser case，或非 build 分数引用 build case；
- case ID 被用作证据目录名，却允许路径分隔符及上级目录。

优化在加载阶段拒绝这些非法定义，并加入 Schema 与临时任务变异回归测试。所有现有 active/retired 任务已满足这些不变量，因此这不是修改既有评分含义。入口：`packages/core/src/schema.ts`、`packages/core/src/tasks.ts`。

### 2. 有断言不等于测到了对应能力 — 下一 Benchmark minor

| 任务/案例 | 当前实际观测 | 缺口与下一版建议 |
| --- | --- | --- |
| 2048 `directional-move` | `lastMove=down`、`spawnCount=1` | 没有检查下移后的棋盘。验证整盘压缩、合并、分数与合法生成位置；补无合法移动的失败状态。 |
| 扫雷 `flood-expansion` | `revealedSafe > 20` | 计数可正确而单元格集合错误。核对连通区域、边界数字、雷格未被展开和计数一致性。 |
| 停车 `collision` | 碰撞次数 1、速度接近 0 | 未验证车体实际停在障碍外。检查姿态、碰撞边界以及穿透。 |
| 停车 `parking-criteria` | 已停好的正例变为 won | 缺少错角度、部分越界、仍在移动等负例，不能充分证明停车判定。 |
| 停车 `distinct-levels` | level 与 levelSignature | 标签不证明布局变化。比较障碍、车位及起点几何。 |
| 原生输入 | 每题少数键盘/点击转移 | 不足以证明所有 UI 控件与 Bridge 共用逻辑。增加同一起点下的状态等价检查，而不是只检查标签。 |

证据均在 `benchmark/tasks/build/*/*/tests/cases.json`。此外，扫雷 `state.schema.json` 的 cells 只约束为 array，未约束行列及 cell 字段；Schema 通过不等于棋盘形状或语义不变量成立。这些案例与 Schema 不应原地改写：加强断言会改变得分，需要新的 task major 和 Benchmark minor，并保留旧包。

### 3. 校准应证明“能识别错误”，不只是“正确实现能通过”

原 `tools/calibrate-poker.mjs` 只验证一个德扑参考实现达到 100。正对照证明案例联合可满足，不能证明案例能排除有缺陷实现。本次加入四种可编译且初始 Schema 正确的规则/UI 变异体：短 all-in 错误重开下注、奇数底池丢筹码、不识别 A2345 顺子、原生 Check 按钮失效。每个变异体要求**指定案例失败且 build gate 通过**，避免把构建失败误当成机制检测成功；两次正对照同时比较源码 hash、完整通过/失败向量和总分。全部变异只发生在临时副本，不改参考原件。

CI 另有一个环境前提缺口：`pnpm check` 已经会启动真实 Chromium，但原 `ci.yml` 只安装 pnpm 依赖，没有安装 Playwright 对应的浏览器。现增加显式 `playwright install --with-deps chromium`，不依赖宿主机或缓存偶然具备浏览器；原 starter 独立冷缓存 smoke 保持不变。

少量变异测试仍不等于完整 mutation coverage。其他三题尚缺同等的仓库维护参考实现与规则变异矩阵。下一阶段应逐项建立“需求 → 案例 → 正确参考 → 有缺陷实现”的追踪关系，尤其是普通非 fixture 的完整游戏过程。

### 4. 单样本与等时限不能支持稳定实力或等算力结论 — 本次澄清

- 每个系统每题只有一次开发观测，不能估计开发采样方差；不要把小分差写成显著优劣。
- 四题分数的离散程度反映题间差异，不是模型均值的置信区间。一个交付里的多个案例也不是独立模型样本。
- 相同 3600 秒预算和一次 Agent invocation 不等于相同 token、推理预算、工具调用或费用。
- 同一 release 下跨 Campaign 排名仍是描述性的；Provider、模型别名、Agent/主机环境和执行日期可能变化。
- 保持既有 Build 主指标；展示单题向量与 hard gate 原因，不进行事后改权、最佳样本选择或补零/删零。

已在 `docs/methodology.md` 和公开站点 methodology 页面明确这些边界。未来可靠性研究应预注册多个独立开发系列并报告全部计划样本；不要为已有 0.6 结果伪造置信区间。

现有公开数据说明了为何需要单题展示：GLM 5.3 Flash 的四题向量为 `100/0/100/0`，GLM 5.3 为 `100/100/0/0`，Build 都是 50，但失败分布不同（对应系列 `01M1C3ECWM6VSC1ZBXQBW32PET`、`01M1EHSCF83P18BXNDAC4YFDS3`）。原榜单用行号当名次，即使总分相同也显示不同名次；本次改为竞赛并列名次 `1,2,2,4`，稳定排序用的 ID 不再充当实力排序依据，缺失分数不赋名次。并显示 provider、thinking、Campaign 来源及可展开的单题/硬门槛结果，不改变原总分或身份 hash。

### 5. 评测器中的评分相关风险 — 需版本化验证，不在本次偷偷修分

- `packages/evaluator/src/evaluate.ts` 的 `jsonEqual` 使用 `JSON.stringify`，JSON 对象键的插入顺序会影响相等比较。下一版应使用键顺序无关的结构比较，并保留数组顺序语义；添加嵌套对象、null、数组的回归。
- 依赖安装失败的基础设施识别只读取 `build.stderr.log`，而包管理器也可能把诊断写入 stdout。应通过 stdout/stderr 双通道故障注入区分真实网络失败、错误依赖、锁文件失败和安装脚本超时，再确定版本化分类规则。
- 三个旧任务 prompt 仍提到 `$CAGB_SEED`，但当前开发 invocation 未注入该变量；真正的种子契约是评测阶段 `reset({seed})`。这是冻结 prompt 的遗留不一致，下一任务版本应删除误导文字，而不是临时改变 Agent 输入。

当前七份公开记录中可见的对象比较失败包含实际字段值差异（如德扑 bot call 的 amount 为 0 而非 2），并未提供“仅键顺序导致误判”的证据。因此不能据此声称某个已发布分数应上调，也不进行推测性重评分。

上述问题可能改变任务的通过/失败或可评分性；根据 `docs/versioning.md`，修复必须进入新 Benchmark minor。当前 release 的 source hash 和完整 Git commit 是审计依据，不能只看版本字符串假定跨提交评测完全等价。

## 后续优先级与验收

1. **当前版本质量控制**：拒绝不可靠任务定义；正/负校准；保留冷缓存 starter smoke；完整 `pnpm check` 和真实 `pnpm cagb doctor`。
2. **下一 minor 的测量有效性**：先补四题参考与机制变异，修复具体观测/比较问题，再冻结新题包和新 release；每个新增案例都需要正确实现通过、对应缺陷实现失败的证据。
3. **下一独立研究的可靠性**：预注册重复开发、执行顺序与系统配置，完整发布样本。报告样本数与局限，不把更多评测种子当作更多独立开发样本。

不增加生产部署，不调用付费 Agent，不改历史系列，不用 UI/文案变更掩盖评分协议变化。

## 审查阶段验证结果（0.6.1 版本整理前）

使用 Node.js `22.22.0`、pnpm `10.33.0`：

- `pnpm check` 通过：99 项单元/集成测试（core 57、site 23、evaluator 19），类型检查、构建、release/历史结果校验、独立冷缓存 starter smoke 全部通过。
- 德扑校准两次正对照均为 100，源码 hash 与测试向量一致；4 个源码变异体均通过 build gate，且各自目标 case 失败，无额外案例回归。
- `pnpm cagb doctor` 通过真实安装、离线重装、构建、预览、Chromium 和 Bridge 预检。
- 生成的静态榜单经过 Playwright 验证：7 行，名次为 `1,2,3,4,5,5,7`，28 项任务分数、7 个 hard-gate 标记、Campaign/provider 信息正确；无页面脚本错误，390px 视口无文档级横向溢出。
- active/retired 任务、既有 release lock、参考实现和历史结果未修改。以上是本地审查记录；后续 0.6.1 发布状态及精确提交的 CI 以 [GitHub Release](https://github.com/Carrick-K7/carrick-ai-gamebench/releases/tag/v0.6.1) 和 Actions 记录为准，不代表生产部署。
