# GameBench 0.7.0 — independent Build / Play, simpler shared infrastructure

This release adds a visual game-playing instrument beside the unchanged Build
benchmark and consolidates execution, qualification, publication and presentation.
It is a **software and frozen-protocol release**, not a new measured model
Campaign or production deployment.

## Independent measurements

- **Build:** the same four tasks, task hashes, one development invocation per
  task, frozen source, canonical seed `104729` and equal-weight score as 0.6.
- **Play / 2048:** ten fresh screenshot/native-input episodes, at most 200
  decisions each, ranked by mean native game score.
- **Play / Minesweeper:** ten 10×10/10-mine episodes, at most 128 decisions each,
  ranked by win percentage. Boards are not guaranteed guess-free.
- There is no Build/Play aggregate and no cross-game Play total. Play uses
  maintainer-owned deterministic games, never a generated Build submission.
- The player receives the current screenshot, rules and bounded action/memo
  memory. Hidden state and seeds are not player tools. Campaigns commit paired
  seed bundles before execution and disclose them only after every cell finishes.

## Architecture simplification

- **One Campaign commit rule:** every cell must share the same real recorded Git
  commit. Execution, batch publication and public-reader checks use the shared
  rule; individually clean but different commits are rejected.
- **One publication transaction:** all result generations publish checked
  snapshots through the same locked, atomic index writer. Indexed records are
  immutable. An interrupted unindexed file can be reused only when its bytes
  exactly match the checked snapshot; conflicting files are never overwritten.
  Existing locks are never automatically stolen, including stale or unconfirmed
  owners; crash recovery requires operator inspection.
- **One Build task-batch policy:** legacy and current envelopes share the
  one-attempt task loop and failure evidence handling. Current results are
  assembled directly as v3, not routed through a synthetic v2 result.
- **Direct flat-result presentation:** current Build pages use real task rows and
  qualification rather than synthesizing legacy Submission/Evaluation/Publication
  entities or empty Core/Reproduce fields. Historical pages keep their adapters.
- **Bounded evidence hashing:** one Play check reuses unchanged file digests across
  nested seals. Filesystem identity, nanosecond timestamps, directory membership,
  file kinds, manifest bytes and expected hashes remain checked. New checks never
  inherit a cache. Engine and native-browser replay remain distinct.

No new package platform, database, queue, scheduler, provider SDK in Core/Evaluator,
Docker requirement, verifier service or deployment target is introduced.

## Compatibility

ReleaseLock v4, Campaign v2 and flat result v3 select the new instruments while
retaining the existing canonical paths and single `results/lite/index.json`.
Older release locks, Campaign Plans, task sources, published results, scores,
identity hashes and URLs are unchanged. No old cell is rerun or relabeled as 0.7.

The public site has separate Play rankings and explicitly unranked human practice.
Absent results are shown as absent, not invented zero scores. Public artifact
links require actually published artifacts; a hash alone is not a download.

## Verification and operation

Use Node.js **22.22.0**, pnpm **10.33.0**, the pinned Playwright Chromium and an
external audited **Pi 0.84.3** installation. A different global Pi can stay in
place: point `PI_BIN` at a separate installation as described in
[Play operations](../play-operations.md).

Release gates are `pnpm check`, `pnpm cagb doctor --suite build`,
`pnpm cagb doctor --suite play`, the exact source commit's CI and the immutable
tag's release workflow. Tests and calibration use synthetic players and real
reference games/browsers, not paid model inference. Release artifacts bind the
source commit and frozen lock with SHA-256 checksums.

## Interpretation limits

Build still observes one development per task; Play's ten episodes per game are
small descriptive samples. Calibration and replay do not create independent model
samples or establish statistically stable superiority. Cross-Campaign comparisons
remain descriptive. Official is maintainer-operated and auditable, not trustless
or an attestation of proprietary model weights. New paid measurements and any
production runtime require separate approval.
